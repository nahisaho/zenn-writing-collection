# なぜID保護が児童生徒の個人情報を守るのか

## 教職員アカウント侵害がもたらす被害

教職員のアカウントが侵害されると、攻撃者は以下のような児童生徒の個人情報にアクセスできてしまいます：

- **成績情報**: 通知表、定期テスト、内申点
- **健康情報**: 既往症、アレルギー、健康診断結果、保健室来室記録
- **家庭環境**: 保護者の職業、収入状況、家族構成
- **要配慮情報**: いじめ・不登校に関する記録、相談記録

実際の事例では、教職員アカウントが侵害されてから発覚まで**平均197日**かかっています。この間、攻撃者は自由に児童生徒の個人情報にアクセスし続けていました。

**本章で構築するID基盤は、このような被害を防ぐための最重要な防御策です。**

# ゼロトラストの出発点 - ID保護

第4章で、A5が教育委員会に必要な理由を見てきました。本章からは、A5の具体的な実装に入ります。

ゼロトラストセキュリティの第一原則は「明示的な検証(Verify Explicitly)」です。この実現には、強固なID基盤が不可欠です。教職員のアカウントが侵害されれば、どれほど高度なセキュリティ製品を導入しても意味がありません。

本章では、Microsoft Entra ID(旧Azure Active Directory)を使った教職員ID基盤の構築方法を、以下の順序で解説します:

1. **教育機関を標的としたアカウント侵害の現状** - なぜID保護が最優先なのか
2. **ID基盤の設計原則** - 教育機関に適した設計方針
3. **Entra IDクラウド専用アカウントの作成** - 実装の基礎
4. **全教職員へのMFA展開** - 最優先の対策
5. **パスワードレス認証の導入** - セキュリティと利便性の両立
6. **Identity Protectionによる自動保護** - A5による高度な防御

# 5.1 教育機関を標的としたアカウント侵害の現状とトレンド

## 教育機関におけるアカウント侵害の深刻化

教育委員会の情報担当者にとって、もっとも恐れるべきは「気づかないうちに教職員アカウントが侵害され、児童生徒の個人情報が漏洩している」状況です。

**統計データ(Microsoft セキュリティレポートより)**:

| 指標 | 数値 | 意味 |
|------|------|------|
| **アカウント侵害の99.9%** | パスワードベース攻撃 | パスワードが最大の脆弱性 |
| **パスワードスプレー攻撃** | 全体の70%以上 | もっとも多い攻撃手法 |
| **教育機関の被害** | 全業種で最高 | 金融・医療の2倍以上 |
| **侵害の平均検知時間** | 197日 | 約6か月間気づかない |

**教育機関が狙われる理由**:

教育機関は、一般企業に比べてアカウント侵害を受けやすい環境にあります。攻撃者にとって価値の高い個人情報が大量に保管されている一方で、セキュリティ対策のリソースが限られているためです。以下、教育機関が標的とされる4つの主要な理由を解説します。

1. **児童生徒の個人情報が大量に存在**
   - 氏名、住所、成績、家庭環境、健康情報
   - 個人情報保護法上の要配慮個人情報を含む
   - ダークウェブでの取引価値が高い

2. **セキュリティ予算・人材の不足**
   - 専任のセキュリティ担当者がいない
   - 一般企業に比べて予算が限られている
   - 対策の優先度が低くなりがち

3. **教職員のITリテラシーのばらつき**
   - セキュリティ意識の個人差が大きい
   - フィッシングメールを見分けられない
   - 弱いパスワードを使用する傾向

4. **多数のアクセスポイント**
   - 保護者、地域、ベンダー、他自治体との連携
   - 境界が曖昧で攻撃対象領域が広い

## パスワードスプレー攻撃とは

教育機関を標的とした攻撃の70%以上を占める「パスワードスプレー攻撃」について、詳しく見ていきます。

### 攻撃の仕組み

```
パスワードスプレー攻撃の流れ:

ステップ1: 攻撃者が一般的なパスワードリストを準備
- "Password123"
- "Spring2024"
- "Welcome123"
- "School2024"
- "Summer2024"

ステップ2: 教育委員会の全教職員アカウント(500名)に対して試行
- 各アカウントに対して1-2回だけ試行
- アカウントロックアウトを回避

ステップ3: 弱いパスワードを使っている教職員を発見
- 500名中5名(1%)が"Spring2024"を使用していた
- これらのアカウントが侵害される

ステップ4: 侵害されたアカウントで校務システムにアクセス
- 児童生徒の個人情報を窃取
- ランサムウェアを展開
- 保護者を装ったフィッシングメールを送信
```

### 従来のブルートフォース攻撃との違い

パスワードスプレー攻撃は、従来のブルートフォース攻撃とは戦略が異なります。ブルートフォース攻撃は「1つのアカウントに対して多数のパスワードを試す」のに対し、パスワードスプレー攻撃は「多数のアカウントに対して少数のよく使われるパスワードを試す」という逆転の発想です。この違いにより、従来のセキュリティ対策(アカウントロックアウト等)では防げないという特徴があります。

| 攻撃手法 | ブルートフォース攻撃 | パスワードスプレー攻撃 |
|---------|-------------------|---------------------|
| **対象** | 1つのアカウント | 多数のアカウント |
| **試行パスワード** | 多数(数万〜数百万) | 少数(10-50個程度) |
| **検知されやすさ** | 検知されやすい | 検知されにくい |
| **アカウントロック** | 発動する | 発動しない |
| **成功率** | 低い | 高い(弱いパスワード使用者がいれば) |

**ポイント**: パスワードスプレー攻撃は、従来のアカウントロックアウト機能では防げません。

### 教育現場での実例シナリオ

**シナリオ1: 一般的なパスワードの使用**

```
攻撃者: "Spring2024"を全教職員アカウント(500名)に試行

結果: 5名の教職員が同じパスワードを使用していたため侵害

被害:
- 侵害された教職員が担任する児童生徒の個人情報が流出
- 成績データが外部に送信される
- 保護者を装った不審なメールが送信される
```

**シナリオ2: 組織名を含むパスワード**

```
攻撃者: "School2024"、"City2024"などを試行

結果: 10名の教職員アカウントが侵害

被害:
- 侵害されたアカウントから校務支援システムにアクセス
- 成績情報が外部に送信
- 6か月間気づかず、被害が拡大
```

**シナリオ3: パスワード定期変更の弊害**

```
教職員: 3か月ごとのパスワード変更を求められる
→ "Spring2024" → "Summer2024" → "Autumn2024"と変更

攻撃者: 季節を含むパスワードパターンを試行
→ 予測可能なパターンで簡単に侵害

被害:
- メールアカウントが侵害
- 保護者宛に偽のフィッシングメールが送信
- 教育委員会の信用が失墜
```

## パスワードスプレー攻撃が成功する3つの理由

### 1. 弱いパスワードの使用

**教育現場でよく使われる危険なパスワード**:

| パスワード例 | 危険度 | 理由 |
|------------|--------|------|
| "Password123" | 🚨極めて危険 | 最低限の複雑性要件のみ満たす |
| "School2024" | 🚨極めて危険 | 組織名+年の組み合わせ |
| "Welcome123" | 🚨極めて危険 | よく使われるパターン |
| "Spring2024" | 🚨極めて危険 | 季節+年の組み合わせ |
| "Abc12345!" | 🚨極めて危険 | 連続文字+数字+記号 |

**なぜ弱いパスワードが使われるのか**:

- 複雑なパスワードは覚えにくい
- 複数のシステムで異なるパスワードを管理できない
- パスワード管理ツールを使っていない
- セキュリティよりも利便性を優先

### 2. パスワード定期変更の弊害

**従来の常識**:
- 「パスワードは3か月ごとに変更すべき」
- 「定期変更はセキュリティのベストプラクティス」

**現在の推奨(NIST/Microsoft)**:
- ❌ **パスワード定期変更は廃止すべき**
- ✅ **侵害の証拠がない限り変更不要**
- ✅ **代わりにMFA・パスワードレス認証を導入**

**定期変更の問題点**:

```
教職員A: "Spring2024"を設定
↓ 3か月後、変更を強制される
教職員A: "Summer2024"に変更
↓ さらに3か月後
教職員A: "Autumn2024"に変更

攻撃者: このパターンを学習し、予測可能に
→ パスワードスプレー攻撃で簡単に侵害
```

**定期変更が生む悪循環**:
1. 複雑なパスワードを設定
2. 覚えられないのでメモする
3. 定期変更を求められる
4. 覚えやすいパターンで変更(Spring2024→Summer2024)
5. 攻撃者に予測されやすくなる

### 3. 検知の難しさ

**なぜパスワードスプレー攻撃は検知されにくいのか**:

パスワードスプレー攻撃がもっとも厄介な理由は、従来のセキュリティ対策をすり抜けるように設計されていることです。各アカウントへの試行回数を少なく抑え、多数のIPアドレスから分散して攻撃するため、正常なサインイン失敗と区別がつきません。以下、主要な検知手法ごとにその限界を見ていきます。

| 検知手法 | 効果 | 理由 |
|---------|------|------|
| **アカウントロックアウト** | ✗ 無効 | 1アカウント1-2回の試行のためロックされない |
| **IPブロックリスト** | △ 限定的 | 攻撃者は多数のIPアドレスを使用(ボットネット) |
| **ログ分析** | △ 困難 | 正規のサインイン失敗と区別がつかない |
| **SIEM** | △ 高コスト | 専門知識と高度な分析が必要 |

**A3での検知の限界**:

```
A3環境での典型的なログ:

2024-06-01 09:00:00 | teacher001@city.ed.jp | サインイン失敗 | IP: 203.0.113.1
2024-06-01 09:05:00 | teacher002@city.ed.jp | サインイン失敗 | IP: 203.0.113.2
2024-06-01 09:10:00 | teacher003@city.ed.jp | サインイン失敗 | IP: 203.0.113.3
...
2024-06-01 10:00:00 | teacher050@city.ed.jp | サインイン成功 | IP: 203.0.113.50

→ 各アカウントは1回ずつの失敗で、異なるIP
→ 手動で相関分析しない限り、パスワードスプレー攻撃と気づけない
→ 侵害されたteacher050のアクセスは「正常」に見える
```

## なぜ従来の対策では不十分なのか

### 従来の対策とその限界

多くの教育委員会が実施している従来のセキュリティ対策は、ブルートフォース攻撃には有効でしたが、パスワードスプレー攻撃には効果がありません。それどころか、一部の対策(パスワード定期変更等)はむしろ攻撃を容易にしてしまいます。以下、4つの代表的な対策とその問題点を見ていきます。

**対策1: 複雑なパスワード要件**

```
要件: 英大小文字、数字、記号を含む8文字以上

教職員の対応: "Password1!" ← 最低限の要件を満たすだけ

結果: パスワードスプレー攻撃に対して無防備
```

**評価**: ❌ パスワードスプレー攻撃には効果なし

**対策2: パスワード定期変更**

```
要件: 90日ごとにパスワード変更を強制

教職員の対応:
"Spring2024" → "Summer2024" → "Autumn2024"

結果: むしろ攻撃者に予測されやすくなる
```

**評価**: ❌ 逆効果(NIST/Microsoftは廃止を推奨)

**対策3: アカウントロックアウト**

```
要件: 同一アカウントへの5回の失敗でロック

パスワードスプレー攻撃の特徴:
1アカウント1-2回の試行のためロックされない

結果: パスワードスプレー攻撃には効果なし
```

**評価**: ❌ パスワードスプレー攻撃には無効

**対策4: IPアドレスブロック**

```
対策: 不審なIPアドレスをブロック

攻撃者の対応:
多数のIPアドレスを使用(ボットネット、VPN等)

結果: すべてのIPをブロックすることは不可能
```

**評価**: △ 限定的な効果

## Microsoft 365 A5が提供する根本的な対策

従来の対策が無効な中、A5は以下の4つの根本的な対策を提供します。

### 対策1: Identity Protection(リスクベース認証) - A5専用

**仕組み**:
- Microsoftの脅威インテリジェンスが不審なサインインパターンを自動検知
- 世界中の65億件/日以上のサインインデータを分析
- ダークウェブで漏洩した認証情報を監視

**パスワードスプレー攻撃への効果**:

```
攻撃者が500アカウントに"Spring2024"を試行

Identity Protectionの検知:
1. 短時間に多数のアカウントへのサインイン失敗を検知
2. パスワードスプレー攻撃のパターンと判定
3. リスクレベルを自動的に「高」に設定

自動対応:
- 該当IPアドレスからのアクセスを一時ブロック
- 管理者に通知
- 影響を受けた可能性のあるアカウントにパスワード変更を促す
```

**A3との違い**:
- A3: Identity Protection なし → 侵害に平均197日間気づかない
- A5: Identity Protection あり → 侵害を数秒で検知・自動ブロック

### 対策2: 多要素認証(MFA)の全教職員展開

**仕組み**:
- パスワード + もう1つの認証要素(スマホアプリ、電話、SMS等)
- パスワードが盗まれても、2つ目の要素がなければアクセス不可

**パスワードスプレー攻撃への効果**:

```
攻撃者が"Spring2024"で教職員Aのアカウント侵害に成功

MFA有効の場合:
1. パスワード認証成功
2. MFA要求: Microsoft Authenticatorアプリで承認が必要
3. 攻撃者はアプリにアクセスできないためブロック

結果: パスワードが盗まれてもアカウント侵害を防げる
```

**重要**: MFAはA3でも利用可能な基本機能です。全教職員への展開が最優先の対策です。

### 対策3: パスワードレス認証への移行

**仕組み**:
- Windows Hello(顔認証・指紋認証)
- FIDO2セキュリティキー
- パスワード自体が存在しない

**パスワードスプレー攻撃への効果**:

```
パスワードレス認証を導入した場合:

攻撃者が"Spring2024"を試行
→ そもそもパスワードが存在しない
→ パスワードスプレー攻撃が不可能

結果: パスワードに依存した攻撃がすべて無効化
```

**追加メリット**:
- フィッシング攻撃にも完全耐性
- 利便性の向上(顔認証で素早くサインイン)
- ヘルプデスク負荷軽減(パスワードリセット依頼が激減)

### 対策4: Conditional Access(高度なアクセス制御)

**仕組み**:
- サインイン時の状況(場所、デバイス、リスクレベル等)に応じた動的な制御
- A5ではリスクレベルベースの制御が可能

**パスワードスプレー攻撃への効果**:

```
攻撃者が海外から校務システムへアクセス試行

Conditional Accessポリシー:
条件: サインイン場所が日本国外
アクション: アクセスをブロック

結果: 海外からのパスワードスプレー攻撃を完全ブロック
```

## 本章で実装する対策

本章では、以下の対策を段階的に実装します:

| 段階 | 対策 | 期間 | A5必須 | 効果 |
|------|------|------|--------|------|
| **第1段階** | 全教職員へのMFA展開 | 1-2か月 | ✗ | パスワード侵害後のアクセスを防ぐ |
| **第2段階** | パスワードレス認証への移行 | 3-6か月 | ✗ | パスワードスプレー攻撃を無効化 |
| **第3段階** | Identity Protectionによる自動保護 | 1か月 | ✅ | 侵害を自動検知・ブロック |

これらの対策により、**パスワードスプレー攻撃の成功率を99%以上削減**できます。

**重要なポイント**:
- MFAは第1段階で必ず実装(A3でも可能)
- A5のIdentity Protectionにより、侵害を自動検知・ブロック
- パスワードレス認証で、パスワードに依存した攻撃をすべて無効化

# 5.2 教育委員会におけるID基盤設計の考え方

本節では、教育機関に適したID基盤の設計原則を解説します。

## 設計の5つの原則

強固なID基盤を構築するには、教育機関の特性を踏まえた設計原則が必要です。本節では、アカウント管理方針、クラウドネイティブIDの採用、組織構造の設計、グループ戦略、自動化の5つの原則を解説します。これらの原則に従うことで、セキュリティと運用性を両立したID基盤を実現できます。

### 原則1: 校務用と学習用のアカウント管理方針

第3章で解説した通り、本書では「単一アカウント型」を前提としています。

**アプローチ2: 単一アカウント型(本書の前提)**

```
教職員: 1つのアカウントで校務と学習の両方を実施

teacher001@city.ed.jp
├── 校務用途: 成績入力、校務支援システム
└── 学習用途: Teams授業、課題配信

メリット:
✅ 教職員の利便性が高い
✅ アカウント管理が単純

デメリット:
⚠️ セキュリティポリシーの設計が複雑
⚠️ 誤操作のリスク(学習用Teamsに成績ファイルを共有等)

対策:
→ 秘密度ラベルとDLPで保護
→ Conditional Accessで用途別に制御
```

**重要**: 単一アカウント型では、情報保護(第10章)の徹底が不可欠です。

### 原則2: クラウドネイティブIDの採用

**推奨: Entra IDクラウド専用アカウント**

```
Entra IDクラウド専用:
teacher001@city.onmicrosoft.com

メリット:
✅ オンプレミスActive Directoryが不要
✅ 同期の複雑性・遅延がない
✅ クラウドの機能をフル活用
✅ コストが低い

デメリット:
⚠️ オンプレミスシステムとの統合が必要な場合は検討が必要
```

**非推奨: ハイブリッドID(オンプレミスAD + Entra ID Connect)**

```
オンプレミスActive Directory
↓ Entra ID Connect で同期
Entra ID

デメリット:
```

### 原則5: 動的グループによる自動化

**動的グループの活用**:

```
グループ名: SG-School-Elementary1-Teachers

(user.department -eq "第一小学校") -and (user.jobTitle -eq "教諭")

- 異動・退職時に自動的に削除

```

**動的グループの設定例**:


**重要**: 動的グループはEntra ID P1以上(A3/A5に含まれる)で利用可能です。

### PowerShellによる一括作成

**前提条件**:
- Microsoft Graph PowerShell SDK のインストール
- グローバル管理者またはユーザー管理者権限

**スクリプト例**:

```powershell
# Microsoft Graph モジュールのインストール(初回のみ)
Install-Module Microsoft.Graph -Scope CurrentUser

# Microsoft Graphに接続
Connect-MgGraph -Scopes "User.ReadWrite.All", "Group.ReadWrite.All"

# CSVファイルの読み込み
$users = Import-Csv -Path "user-import.csv" -Encoding UTF8

# 各ユーザーの作成
foreach ($user in $users) {
    # パスワードプロファイルの作成
    $passwordProfile = @{
        Password = "TempPassword123!" # 初期パスワード(初回サインイン時に変更強制)
        ForceChangePasswordNextSignIn = $true
    }

    # ユーザーパラメータの設定
    $userParams = @{
        DisplayName = $user.displayName
        UserPrincipalName = $user.userPrincipalName
        MailNickname = $user.mailNickname
        GivenName = $user.givenName
        Surname = $user.surname
        JobTitle = $user.jobTitle
        Department = $user.department
        UsageLocation = $user.usageLocation
        AccountEnabled = [System.Convert]::ToBoolean($user.accountEnabled)
        PasswordProfile = $passwordProfile
    }

    # ユーザーの作成
    try {
        New-MgUser @userParams
        Write-Host "✅ ユーザー作成成功: $($user.displayName)" -ForegroundColor Green
    }
    catch {
        Write-Host "❌ ユーザー作成失敗: $($user.displayName) - $_" -ForegroundColor Red
    }
}

# 接続を切断
Disconnect-MgGraph
```

## ライセンスの自動割り当て

100名規模の教育委員会では、ライセンスを手動で割り当てると管理負荷が大きくなります。グループベースのライセンス割り当てを使用することで、ユーザーがグループに追加されると自動的にライセンスが付与され、削除されると自動的に回収されます。これにより、入職・異動・退職時の作業を大幅に削減できます。

**グループベースのライセンス割り当て(推奨)**:

```
セキュリティグループを使ったライセンス自動割り当て:

1. セキュリティグループ作成:
   グループ名: SG-License-A5-Faculty
   タイプ: セキュリティ
   メンバーシップ: 動的
   ルール: (user.jobTitle -ne "")

2. グループにライセンスを割り当て:
   [グループ] → [SG-License-A5-Faculty] → [ライセンス]
   → [+ 割り当て]
   → [Microsoft 365 A5 for Faculty] を選択

3. 効果:
   - グループに追加されたユーザーに自動的にA5ライセンスが付与
   - グループから削除されると自動的にライセンスが回収
   - 手動割り当ての管理負担を削減
```

**PowerShellでのライセンス割り当て**:

```powershell
# ライセンスSKUの確認
Get-MgSubscribedSku | Select-Object SkuPartNumber, SkuId

# A5 Facultyライセンスの割り当て
$skuId = "M365EDU_A5_FACULTY" # SkuPartNumberは環境により異なる

# ユーザーへのライセンス割り当て
$userUpn = "yamada.taro@city.onmicrosoft.com"
$license = @{
    SkuId = $skuId
}

Set-MgUserLicense -UserId $userUpn -AddLicenses @($license) -RemoveLicenses @()
```

## 初期パスワードポリシー

Entra IDのパスワードポリシーは、アカウント侵害を防ぐための最初の防御線です。しかし、5.1節で解説した通り、従来の「複雑なパスワード+定期変更」というアプローチは逆効果です。本節では、NIST/Microsoftの最新推奨に基づいた、教育機関に適したパスワードポリシーを設定します。

**パスワードポリシーの設定**:

```
Entra IDのデフォルトパスワードポリシー:
- 最小文字数: 8文字
- 複雑性要件: 大文字、小文字、数字、記号のうち3種類
- 有効期限: 90日(カスタマイズ可能)
- パスワード履歴: 過去24個のパスワードは再利用不可

推奨設定:
✅ 複雑性要件: 有効(デフォルト)
✅ 初回サインイン時のパスワード変更: 必須
❌ パスワード有効期限: 無効(NIST/Microsoft推奨)
✅ セルフサービスパスワードリセット(SSPR): 有効
```

**パスワード有効期限の無効化**:

```powershell
# 組織全体でパスワード有効期限を無効化
Update-MgDomain -DomainId "city.onmicrosoft.com" -PasswordValidityPeriodInDays 2147483647
```

**重要**: パスワード有効期限は無効化し、代わりにMFA・パスワードレス認証・Identity Protectionを実装します。

## アカウントライフサイクル管理

教職員のアカウントは、入職・異動・退職のライフサイクルに応じて適切に管理する必要があります。動的グループとグループベースのライセンス割り当てを活用することで、これらのプロセスの多くを自動化できます。以下、3つの主要なライフサイクルイベントでの推奨手順を示します。

**入職時**:
1. 人事システムから情報を取得
2. Entra IDアカウントを作成
3. 適切なグループに追加(動的グループなら自動)
4. ライセンスが自動的に割り当て
5. 初期パスワードを通知
6. 初回サインイン・MFA登録を案内

**異動時**:
1. Entra IDの部署(department)属性を更新
2. 動的グループのメンバーシップが自動更新
3. 新しい部署のアクセス権が自動付与
4. 旧部署のアクセス権が自動削除

**退職時**:
1. アカウントを無効化(削除ではなく無効化を推奨)
2. 30日間は復元可能
3. 30日後に完全削除(自動)
4. ライセンスは即座に回収

**PowerShellでのアカウント無効化**:

```powershell
# アカウントの無効化
$userUpn = "yamada.taro@city.onmicrosoft.com"
Update-MgUser -UserId $userUpn -AccountEnabled:$false

# 30日以内に復元する場合
Update-MgUser -UserId $userUpn -AccountEnabled:$true
```
