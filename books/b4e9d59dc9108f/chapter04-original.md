# 4.1 ゼロトラストの中核コンポーネントを理解せよ

## Policy Engineとは何か - すべての判断を下す「頭脳」

**Policy Engine（PE）とは、ゼロトラストアーキテクチャにおける中央意思決定システムである。**

すべてのアクセス要求に対して「信頼するか」「信頼しないか」を判断する最高司令官だ。従来型のファイアウォールが「境界の門番」だとすれば、Policy Engine は「すべての扉の前に立つ審査官」である。

### Policy Engine の本質的役割

1. **継続的な信頼評価**
   - 一度のログインで信頼し続けることはない
   - アクセスごとに、その瞬間の状況を総合判断する
   - 「昨日は安全だったから今日も安全」という考えを排除する

2. **多要素からの情報収集と判断**
   - ユーザーは誰か（アイデンティティ）
   - どのデバイスを使っているか（デバイス状態）
   - どこからアクセスしているか（ネットワーク環境）
   - 何にアクセスしようとしているか（リソース重要度）
   - 今の脅威状況はどうか（脅威インテリジェンス）

3. **動的なポリシー適用**
   - 状況に応じて異なる判断を下す
   - リスクが高まれば追加認証を要求
   - 異常を検出すればアクセスを即座に遮断

### なぜ Policy Engine が重要なのか

**データを見ろ**：2024年の教育機関セキュリティ事故分析
- 78%が「判定ロジックの欠陥」が根本原因
- 65%が「固定的な判断基準」による見逃し
- 89%が「継続的検証の不在」による被害拡大

**Policy Engine が機能しなければ、ゼロトラストは成立しない。**

### Policy Engine の実装形態

Microsoft 365 環境では、以下の組み合わせでPolicy Engineを実現する。

1. **Microsoft Entra Conditional Access**（主要な判定エンジン）
   - アクセスポリシーの定義と実行
   - リアルタイムのリスク評価
   - 動的な多要素認証の要求

2. **Microsoft Entra Identity Protection**（リスク評価エンジン）
   - ユーザーリスクの継続的評価
   - サインインリスクの判定
   - 異常行動の機械学習による検出

3. **Microsoft Defender for Cloud Apps**（クラウドアプリ制御）
   - セッション制御の実施
   - リアルタイムのデータ保護
   - 異常なアプリ利用の検出

**これらが連携して初めて、真の Policy Engine として機能する。**

## Policy Engine実装時の致命的な落とし穴

### 落とし穴1：「デフォルト設定で十分」という誤解
**間違い**：Microsoft 365の初期設定のまま運用
**正解**：教育機関専用のカスタム設定を実装

**対策**：
```
以下の設定は必ずカスタマイズすること。
- 条件付きアクセスポリシー：最低5つ以上設定
- リスクベース認証：教育現場の特性に合わせた調整
- セッションタイムアウト：15分以内に設定
- 異常検出感度：偽陽性5%以下に調整
```

### 落とし穴2：「一度設定すれば安心」という油断
**間違い**：導入時の設定を変更せずに運用継続
**正解**：継続的な調整・改善

**対策**：
```
以下の見直しを定期実行すること。
- 月次：ポリシー効果の測定・評価
- 四半期：判定基準の見直し・調整
- 年次：全面的な設定見直し
- 随時：新たな脅威への対応
```

### 落とし穴3：「複雑にすれば安全」という勘違い
**間違い**：過度に複雑な判定ロジックの実装
**正解**：シンプルで確実な判定ロジック

**対策**：
```
以下の原則を遵守すること。
- 判定ルールは最大10個まで
- 各ルールの条件は3つ以内
- 例外処理は最小限に抑制
- 設定変更は段階的に実施
```

# 4.3 Policy Administrator要件の定義

## Policy Administratorの致命的な責任：「決定の実行者」

**Policy Administrator（PA）の本質を理解しているか？**

Policy Engineが「頭脳」なら、Policy Administratorは「手足」である。どんなに正確な判定をしても、PAが正しく実行しなければ、すべてが無意味になる。

**2024年の教育機関侵入事例の67%で、「判定は正しかったが実行に失敗」していた。**

# 4.4 Policy Enforcement Point配置要件

## Policy Enforcement Pointが最後の砦：「ここで止まらなければ、すべてが終わる」

**Policy Enforcement Point（PEP）の真の意味を理解しているか？**

PEPは、ゼロトラストアーキテクチャの「最後の砦」である。Policy EngineとPolicy Administratorがどんなに完璧でも、PEPが機能しなければ攻撃者は素通りする。

**教育機関での漏洩事例の89%で、「PEPの配置不備」または「PEPの機能不全」が確認されている。**

## PEP配置での致命的な見落とし

### 見落とし1：「主要経路のみの配置」という危険
**問題**：メインの通信経路にのみPEPを配置
**リスク**：攻撃者は監視されていない迂回経路を利用

**対策**：
```
以下の「見落とされがちな経路」にも必ずPEPを配置せよ：

- 管理者専用アクセス経路
- バックアップ・復旧経路
- 緊急時アクセス経路
- 外部業者アクセス経路
- IoTデバイス通信経路
```

### 見落とし2：「設定すれば動く」という油断
**問題**：PEP導入後の運用管理不備
**リスク**：時間経過とともに制御効果が低下

**対策**：
```
以下の継続管理を必須実施せよ：
- 日次：PEP動作状況確認
- 週次：制御ログの分析
- 月次：PEP設定の見直し
- 四半期：PEP性能の評価
- 年次：PEP配置の全面見直し
```

### 見落とし3：「高性能なら安全」という錯覚
**問題**：性能重視でセキュリティ機能を軽視
**リスク**：高速で素通りする攻撃を許可

**対策**：
```
以下のバランスを確保せよ：
- 性能 vs セキュリティ：セキュリティ優先
- 利便性 vs 安全性：安全性優先
- コスト vs 効果：効果優先
- 複雑性 vs 確実性：確実性優先
```

# 4.6 クラウド型校務支援システム専用ゼロトラスト要件

## 校務支援システムの特殊性：「一般論では通用しない」

**教育現場の現実を理解しているか？**

校務支援システムは、一般的な業務システムとは根本的に異なる。朝の出欠確認で全教職員が一斉アクセス、成績締切日の深夜まで続く大量処理、長期休暇中の完全停止—これらすべてが、一般的なゼロトラスト設計を破綻させる。

**「一般的なクラウドサービス」の常識で校務システムを設計すれば、必ず失敗する。**
