**この章で学べること**：
- 調達仕様書の標準構成と各セクションに記載すべき必須要素
- 曖昧な要件記載がもたらすリスクと具体的記載方法への転換技法
- ベンダー評価基準の設定方法と提案書チェックポイント
- 教育機関特有の調達制約（予算・人員・スケジュール）への対処法
- 契約後のトラブル防止のための責任分界点の明確化手法
- 調達担当者が犯しやすい致命的ミスとその回避策

**なぜこの章が重要なのか**：
第1章で現状の危機を認識したが、解決への第一歩は「正しい調達仕様書の作成」である。99%の教育機関が「適切なセキュリティ対策を講じること」という曖昧な記載で調達を進め、結果として不十分なシステムを導入している。本章で学ぶ構造化された仕様書作成手法こそが、子どもたちの個人情報を守る確実なシステム調達への道筋となる。

# 2.1 調達仕様書の標準構成

## 「セキュリティ対策を実施すること」―この一文が悲劇を生む

あなたの仕様書に、こんな文言が書かれていないか？

- 「適切なセキュリティ対策を講じること」
- 「情報漏洩の防止に努めること」
- 「必要に応じてセキュリティ機能を実装すること」

**これらはすべて、ベンダーの逃げ道である。**

「適切」とは何か？「必要に応じて」とはいつか？明確な基準がなければ、ベンダーは最低限の対策で「仕様通り」と主張する。

そして、あなたは反論できない。

## 調達仕様書の12セクション：完璧な構成はこれだ

ゼロトラスト型校務支援システムの調達仕様書は、以下の12セクションで構成しなければならない。

### 1. 調達概要（10ページ）
- **目的**：なぜゼロトラストが必要なのか
- **背景**：現在のセキュリティ課題と漏洩リスク
- **期待効果**：数値目標と成果指標

### 2. システム要件（20ページ）
- **基本機能**：校務支援システムとして必須の機能
- **性能要件**：レスポンス時間、同時接続数の明確な基準
- **可用性要件**：99.9%以上のサービス稼働率

### 3. ゼロトラストセキュリティ要件（30ページ）
- **NIST SP800-207準拠**：7原則の完全実装
- **アイデンティティ管理**：多要素認証、条件付きアクセス
- **デバイス管理**：エンドポイント保護、コンプライアンス

### 4. 校務支援システム要件（25ページ）
- **成績処理機能**：評価・評定の自動計算、観点別評価対応
- **帳票管理**：指導要録、通知表、調査書の完全電子化
- **校務データ管理**：児童生徒情報、保健情報、出欠席管理
- **文科省標準仕様準拠**：統合型校務支援システムの標準仕様100%対応
- **ゼロトラストセキュリティ実装**：校務データへの条件付きアクセス、継続的な信頼評価
- **Microsoft 365連携**：Entra ID 統合、SharePoint 文書管理統合

### 5. Microsoft 365 A5 要件（15ページ）
- **ライセンス仕様**：Microsoft 365 A5 の全機能活用
- **ゼロトラスト実装**：Microsoft 365 の5段階ゼロトラスト展開計画に準拠
- **設定要件**：Secure Score で80点以上の達成
- **連携要件**：校務支援システムとの統合認証（SSO）

### 6. データ保護要件（15ページ）
- **データ分類**：校務データの4種類分類
- **暗号化要件**：保存時・転送時の暗号化基準
- **DLP要件**：データ漏洩防止の具体的ルール

### 7. ネットワークセキュリティ要件（10ページ）
- **マイクロセグメンテーション**：動的な分離制御
- **ゼロトラストネットワーク**：信頼境界の完全撤廃
- **監視要件**：24時間365日のネットワーク監視

### 8. 運用保守要件（20ページ）
- **運用体制**：人員配置と役割分担
- **保守対応**：SLA定義と対応時間
- **継続的改善**：月次レビューとPDCAサイクル

### 9. 移行要件（15ページ）
- **段階移行**：リスクを最小化する移行計画
- **データ移行**：既存データの完全移行と検証
- **並行運用**：切り替え時のリスク対策

### 10. 教育訓練要件（10ページ）
- **利用者研修**：教職員向けセキュリティ研修
- **管理者研修**：システム管理者の技術研修
- **継続教育**：年次アップデート研修

### 11. 評価基準（15ページ）
- **技術評価**：機能要件の適合性評価
- **提案評価**：運用体制と実績の評価
- **価格評価**：TCOベースの総合評価

### 12. 契約条件（10ページ）
- **責任範囲**：ベンダーと発注者の責任分界
- **損害賠償**：セキュリティインシデント時の賠償責任
- **契約解除**：重大な不備発生時の解除条件

**総ページ数：185ページ**

「長すぎる」と思うか？短すぎるのである。子どもたちの個人情報を守るのに、手抜きは許されない。

## 各セクションの必達基準

### セクション1：調達概要の必達基準
- **数値目標**：セキュリティインシデント発生率0.1%以下
- **ROI明示**：投資対効果198%の根拠資料
- **期限設定**：16ヶ月以内の完全実装

### セクション3：ゼロトラストセキュリティ要件の必達基準
- **NIST準拠率**：100%（例外なし）
- **実装項目数**：125項目の必須要件
- **検証方法**：第三者機関による適合性評価

### セクション3-2：校務支援システム機能要件の必達基準
- **基本機能カバー率**：文科省標準仕様の100%実装
- **成績処理精度**：計算誤差0%、データ整合性100%
- **帳票出力対応**：指導要録、通知表、調査書等の完全対応
- **校務系データ連携**：既存システムとの双方向データ連携実現
- **UI/UX基準**：教職員の作業時間を30%以上削減

### セクション4：Microsoft 365 A5要件の必達基準
- **Secure Score**：80点以上（常時維持）
- **機能活用率**：A5機能の95%以上を実装
- **統合レベル**：校務支援システムとの完全統合

### セクション7：運用保守要件の必達基準
- **対応時間**：緊急時15分以内、通常時4時間以内
- **稼働率**：99.9%以上（月間停止時間43分以内）
- **改善頻度**：月次での機能改善実施

## 仕様書作成の致命的な落とし穴

### 落とし穴1：「〜程度」「〜相当」の表現
**NG例**：「Microsoft 365 A5 相当の機能を提供すること」
**OK例**：「Microsoft 365 A5 を導入し、全機能を有効化すること」

**理由**：「相当」では代替製品での言い逃れが可能

### 落とし穴2：数値基準の不在
**NG例**：「高いセキュリティレベルを実現すること」
**OK例**：「Microsoft Secure Score で80点以上を達成し、月次で維持すること」

**理由**：測定不可能な要件は検証不可能

### 落とし穴3：責任範囲の曖昧さ
**NG例**：「セキュリティインシデントに対応すること」
**OK例**：「セキュリティインシデント発生時は15分以内に初動対応を開始し、4時間以内に詳細報告書を提出すること」

**理由**：具体的な義務がなければ責任を追及できない

### 落とし穴4：運用フェーズの軽視
**NG例**：「システム導入後は適切に運用すること」
**OK例**：「専任技術者2名以上を配置し、24時間365日の監視体制を構築すること」

**理由**：運用品質が最終的なセキュリティを決定する

次節では、これらの要件をゼロトラストアーキテクチャの中でどこに配置すべきかを明確にする。

# 2.2 ゼロトラスト要件の配置場所

## ゼロトラストは「おまけ」ではない

多くの仕様書で見る最大の誤解がこれである。

**間違った配置例**：
```
第3章 システム機能要件
3.1 基本機能
3.2 オプション機能
3.3 セキュリティ機能（ゼロトラスト含む）
```

**なぜ間違いなのか？**

ゼロトラストを「セキュリティ機能の一部」として扱うと、ベンダーは基本機能を優先し、セキュリティを後回しにする。これは設計思想の根本的誤りである。

## 正しい配置：ゼロトラストファースト

ゼロトラスト型システムでは、**セキュリティが基盤**である。すべての機能がゼロトラスト原則の上に構築される。

**正しい配置例**：
```
第3章 ゼロトラストアーキテクチャ要件
3.1 基本原則（NIST SP800-207準拠）
3.2 アイデンティティ管理
3.3 デバイス管理
3.4 ネットワークセキュリティ
3.1.5 データ保護

第4章 校務支援システム機能要件
4.1 基本機能（ゼロトラスト環境での実装）
4.2 連携機能（Microsoft 365 A5との統合）
4.3 管理機能（セキュリティ監視統合）
```

この配置により、**すべての機能がゼロトラスト原則に従う**ことが明確になる。

## NIST SP800-207の7原則：仕様書への完全実装

### 原則1の仕様書記載例
**要件名**：すべてのリソースの明示的管理
**詳細要件**：
- 校務支援システム、Microsoft 365、すべての端末、プリンター、ネットワーク機器を含むすべてのリソースをアセット管理システムに登録すること
- 未登録リソースのネットワークアクセスを自動的に遮断すること
- リソース台帳の更新頻度は日次とし、差分検出機能を実装すること

**検証方法**：
- アセット管理システムの画面キャプチャ提出
- 未登録デバイス検出テストの実施
- 台帳更新ログの3ヶ月分提出

### 原則2の仕様書記載例
**要件名**：ネットワーク場所非依存のセキュリティ
**詳細要件**：
- 校内・校外を問わず、すべての通信をTLS 1.3で暗号化すること
- VPN接続を使用せず、ゼロトラストネットワークアクセス（ZTNA）を実装すること
- 地理的位置によるアクセス制御を無効化し、デバイス認証とユーザー認証の組み合わせで判定すること

**検証方法**：
- 通信暗号化の技術仕様書提出
- ZTNA機能のデモンストレーション実施
- 地理的制御無効化の設定証明

### 原則3の仕様書記載例
**要件名**：セッション単位のアクセス制御
**詳細要件**：
- すべてのアクセスをセッション単位で認証・認可すること
- セッション継続時間は最大15分とし、15分経過後は再認証を要求すること
- 1つの作業完了時には自動的にセッションを終了すること（成績入力完了時等）

**検証方法**：
- セッション管理機能のテスト実施
- タイムアウト動作の実証
- 自動終了機能のデモンストレーション

### 原則4の仕様書記載例
**要件名**：動的ポリシーによるアクセス決定
**詳細要件**：
- 以下の要素を組み合わせた動的スコアリングを実装すること：
  - ユーザー信頼度（0-100点）
  - デバイス健全性（0-100点）
  - アクセス環境リスク（0-100点）
  - 時間帯係数（0.5-2.0倍）
  - リソース機密度（1-5レベル）
- 総合スコアが閾値（60点）を下回る場合は自動的にアクセス拒否すること
- スコア計算ロジックを可視化し、管理者が確認できること

**検証方法**：
- スコア計算デモンストレーション
- 閾値動作テスト
- 管理画面のスクリーンショット提出

### 原則5の仕様書記載例
**要件名**：継続的資産監視
**詳細要件**：
- すべてのデバイスを15分間隔で自動スキャンし、以下を監視すること：
  - OSパッチ適用状況
  - ウイルス定義更新状況
  - 不正ソフトウェア検出
  - 設定変更履歴
  - 異常通信検出
- 1つでも異常があれば即座にネットワークから隔離すること
- 隔離されたデバイスは修復完了まで業務ネットワークに復帰できないこと

**検証方法**：
- 15分間隔監視の動作確認
- 異常検出シミュレーション
- 隔離・復旧プロセスのテスト

### 原則6の仕様書記載例
**要件名**：厳密な事前認証・認可
**詳細要件**：
- すべてのリソースアクセス前に以下を実施すること：
  - 多要素認証（生体認証 + パスワード + デバイス証明書）
  - デバイスコンプライアンス確認
  - 条件付きアクセスポリシー評価
  - リアルタイム脅威インテリジェンス照合
- これらの確認が完了するまで、一切のデータアクセスを許可しないこと
- 確認処理は3秒以内に完了すること

**検証方法**：
- 認証フロー全体のテスト
- 処理時間測定
- 確認完了前アクセス拒否の実証

### 原則7の仕様書記載例
**要件名**：包括的情報収集と活用
**詳細要件**：
- 以下の情報を24時間365日収集すること：
  - 全アクセスログ（成功・失敗問わず）
  - デバイス状態変更履歴
  - ネットワーク通信パターン
  - アプリケーション使用状況
  - セキュリティアラート
- 収集データは90日間保持し、分析・検索可能な形式で保存すること
- 異常パターン検出AI機能を実装し、脅威の予兆を自動検出すること

**検証方法**：
- ログ収集範囲の確認
- 90日間保持の実証
- AI検出機能のデモンストレーション

## 配置時の注意点：依存関係の明確化

ゼロトラスト要件を配置する際は、**依存関係**を必ず明示せよ。

**依存関係の記載例**：
```
【前提条件】
- Microsoft 365 A5 の導入完了
- 全端末での Intune 登録完了
- Microsoft Entra ID によるアイデンティティ統合完了

【実装順序】
1. アイデンティティ管理実装（1-2ヶ月）
2. デバイス管理実装（2-3ヶ月）
3. ネットワークセキュリティ実装（3-4ヶ月）
4. 校務支援システム統合（4-5ヶ月）
5. 監視・運用開始（5-6ヶ月）
```

これにより、ベンダーは「○○が未完了なので実装できない」という言い訳ができなくなる。

次節では、このような曖昧さを完全に排除する記載テクニックを習得する。

# 2.3 曖昧さを排除する記載テクニック

## 曖昧表現撲滅：5つの致命的ワード

以下の表現が仕様書に1つでもあれば、**即座に書き直せ**。

### 致命的ワード1：「適切に」
**NG例**：「適切にアクセス制御を実施すること」
**なぜダメか**：「適切」の基準が不明

**OK例**：「以下の条件をすべて満たすアクセス制御を実施すること：
- 多要素認証による本人確認
- デバイス証明書による端末認証
- 条件付きアクセスポリシーによるリスク評価
- アクセス許可判定3秒以内完了
- 判定ログの完全記録」

### 致命的ワード2：「必要に応じて」
**NG例**：「必要に応じてセキュリティ機能を追加すること」
**なぜダメか**：「必要」の判断基準が不明

**OK例**：「以下の条件発生時は24時間以内にセキュリティ機能を追加すること：
- Microsoft Secure Scoreが80点を下回った場合
- 新たな脅威パターンが検出された場合
- 監査で不備が指摘された場合
- 利用者数が当初想定の120%を超えた場合」

### 致命的ワード3：「原則として」
**NG例**：「原則として暗号化を実施すること」
**なぜダメか**：例外の範囲が不明

**OK例**：「すべてのデータを以下の基準で暗号化すること。例外は一切認めない：
- 保存時：AES-256による暗号化
- 転送時：TLS 1.3による暗号化
- バックアップ：暗号化されたストレージへの保存
- 一時ファイル：メモリ上でも暗号化維持」

### 致命的ワード4：「努める」
**NG例**：「セキュリティレベルの向上に努めること」
**なぜダメか**：努力目標であり義務ではない

**OK例**：「以下のセキュリティレベルを必ず達成すること：
- Microsoft Secure Score：80点以上
- セキュリティインシデント：月0件
- パッチ適用率：48時間以内に95%以上
- 監査適合率：100%」

### 致命的ワード5：「十分な」
**NG例**：「十分なセキュリティ監視を行うこと」
**なぜダメか**：「十分」の判定基準が不明

**OK例**：「以下の監視を24時間365日実施すること：
- 全アクセスログの記録・分析
- 異常通信の自動検出・通報
- デバイス状態の15分間隔監視
- セキュリティアラート3分以内対応
- 月次レポートによる分析結果報告」

## 数値化の鉄則：すべてを測定可能にせよ

### 数値化テクニック1：時間の明確化
**NG**：「速やかに対応すること」
**OK**：「緊急事態は15分以内、通常事態は4時間以内に対応すること」

### 数値化テクニック2：品質の明確化
**NG**：「高品質なサービスを提供すること」
**OK**：「以下の品質基準を満たすこと：
- システム稼働率：99.9%以上
- レスポンス時間：3秒以内
- データ精度：99.99%以上
- 利用者満足度：4.0以上（5点満点）」

### 数値化テクニック3：セキュリティレベルの明確化
**NG**：「強固なセキュリティを実現すること」
**OK**：「以下のセキュリティレベルを実現すること：
- 不正アクセス検知率：99.7%以上
- 誤検知率：0.1%以下
- 脆弱性修正時間：発見から48時間以内
- セキュリティ教育受講率：100%」

## 具体性の5段階：レベル5を目指せ

### レベル1（最低）：抽象的表現
「セキュリティを強化すること」

### レベル2（不十分）：分野指定
「認証セキュリティを強化すること」

### レベル3（普通）：手法指定
「多要素認証を導入すること」

# 2.4 ベンダーの逃げ道を塞ぐ方法

## ベンダーの典型的逃げ道パターン10選

### 逃げ道1：「技術的に不可能」
**ベンダーの主張**：「その仕様は技術的に実現不可能です」
**実態**：単にコストを抑えたい、技術力が不足している

**塞ぎ方**：事前に技術実現性を証明する参考事例を仕様書に記載
```
【技術実現性の証明】
本要件は以下の事例で実現済みである：
- A市教育委員会（導入実績2024年4月）
- B県立高校（導入実績2024年6月）
- Microsoft公式ドキュメント：〈URL〉
- 技術実現不可能を主張する場合は、技術的根拠資料の提出を義務とする
```

### 逃げ道2：「仕様解釈の相違」
**ベンダーの主張**：「この仕様は別の意味に解釈できます」
**実態**：都合の良い解釈で手抜きしたい

**塞ぎ方**：解釈の余地を完全に排除
```
【解釈の明確化】
本要件における「多要素認証」とは以下を指し、これ以外の解釈は認めない：
- 第1要素：生体認証（指紋、顔、虹彩のいずれか）
- 第2要素：知識認証（パスワード、PIN）
- 第3要素：所有認証（デバイス証明書、ハードウェアトークン）
- 3要素すべてが認証されるまで、一切のアクセスを許可しない
- SMS認証、音声通話認証は多要素認証として認めない
```

### 逃げ道3：「別料金での対応」
**ベンダーの主張**：「その機能は標準外のため追加料金が発生します」
**実態**：後から料金を釣り上げたい

**塞ぎ方**：すべての要件を契約金額に含めることを明記
```
【料金の明確化】
本仕様書記載の全要件は提示価格に含まれるものとする：
- 追加料金の請求は一切認めない
- 「標準外」「オプション」等の理由での追加料金も認めない
- 要件実現に必要なライセンス費用もすべて含む
- 違反した場合は契約違反として契約解除する
```

### 逃げ道4：「段階的実装」
**ベンダーの主張**：「まずは基本機能から実装し、セキュリティは後で強化します」
**実態**：セキュリティを軽視、後回しにしたい

**塞ぎ方**：セキュリティファーストの実装順序を強制
```
【実装順序の固定】
以下の順序での実装を義務とし、変更は認めない：
1. ゼロトラストセキュリティ基盤構築（1-3ヶ月）
2. Microsoft 365 A5設定・連携（2-4ヶ月）
3. 校務支援システム機能実装（3-5ヶ月）
4. 統合テスト・セキュリティ検証（5-6ヶ月）
- セキュリティ要件が未完了の状態では次フェーズに進行不可
- 機能要件よりもセキュリティ要件を優先する
```

### 逃げ道5：「運用でカバー」
**ベンダーの主張**：「その機能は運用でカバーできます」
**実態**：技術実装を避け、手作業に依存させたい

**塞ぎ方**：自動化を強制し、手動運用を禁止
```
【自動化の強制】
以下の処理は必ずシステムで自動化し、手動運用は禁止する：
- ユーザーアカウント作成・削除
- アクセス権限の付与・剥奪
- セキュリティパッチの適用
- ログ分析・異常検知
- インシデント通知・初動対応
- 「運用でカバー」を提案した場合は提案失格とする
```

### 逃げ道6：「業界標準」
**ベンダーの主張**：「業界標準に従って実装します」
**実態**：低いレベルの標準で妥協したい

**塞ぎ方**：具体的な標準と基準を明記
```
【準拠すべき標準の明確化】
以下の標準に完全準拠すること：
- NIST SP800-207（ゼロトラストアーキテクチャ）
- ISO/IEC 27001:2022（情報セキュリティマネジメント）
- NIST Cybersecurity Framework 2.0
- Microsoft Security Baseline for Microsoft 365
- 「業界標準」「一般的」等の曖昧な表現での代替は認めない
```

### 逃げ道7：「パフォーマンス懸念」
**ベンダーの主張**：「セキュリティを強化するとパフォーマンスが低下します」
**実態**：コストのかかる高性能機器を避けたい

**塞ぎ方**：パフォーマンス基準とセキュリティ基準の両立を義務化
```
【パフォーマンス基準の設定】
以下の基準を同時に満たすこと：
- セキュリティ：Microsoft Secure Score 80点以上
- パフォーマンス：画面表示3秒以内
- 可用性：99.9%以上の稼働率
- 同時接続：800名の同時アクセス対応
- いずれか1つでも基準未達成の場合は不合格とする
```

### 逃げ道8：「将来的対応」
**ベンダーの主張**：「その機能は将来的に対応予定です」
**実態**：実装を先送りし、契約後に立場を有利にしたい

**塞ぎ方**：すべての機能の完成時期を契約書に明記
```
【完成時期の確定】
全機能の完成時期を以下の通り確定する：
- 基本機能：契約から6ヶ月以内
- セキュリティ機能：契約から3ヶ月以内
- 連携機能：契約から4ヶ月以内
- 管理機能：契約から5ヶ月以内
- 1日でも遅延した場合は遅延損害金を請求する
```

### 逃げ道9：「既存システム制約」
**ベンダーの主張**：「既存システムの制約で実装できません」
**実態**：既存システムとの連携コストを避けたい

**塞ぎ方**：既存システム調査を事前実施させ、対策を義務化
```
【既存システム対応の義務化】
既存システムとの連携は必須要件とする：
- 契約前に既存システムの詳細調査を実施
- 連携できない場合の代替案を事前提示
- 連携実現に必要な改修もすべて対応
- 「既存システム制約」を理由とした機能削減は認めない
```

### 逃げ道10：「他社責任」
**ベンダーの主張**：「その部分は Microsoft の責任です」
**実態**：責任範囲を曖昧にして問題を回避したい

**塞ぎ方**：ベンダーの統括責任を明確化
```
【統括責任の明確化】
以下の責任はすべてベンダーが負う：
- Microsoft 365の設定・運用・保守
- 他社製品との連携不具合
- サードパーティ製品の障害対応
- 利用者への技術サポート
- 「他社の責任」「責任範囲外」等の主張は認めない
```

```
5. 質疑応答（制限時間：10分）

【実証失敗時の扱い】：
実証に1つでも失敗した場合は即座に失格とする
```

**ベンダーは「できる」と言った以上、必ず実証できなければならない。**

```
【原則1】すべてのデータソースとコンピューティングサービスをリソースと見なす
■実装要件
- 校務支援システム、Microsoft 365、端末、プリンター、ネットワーク機器を含むすべてのリソースをアセット管理システムに登録
- 未登録リソースの自動検出・遮断機能
- リソース台帳の日次自動更新
■検証方法
- アセット管理画面のデモンストレーション
- 未登録デバイス検出テストの実施
- 台帳更新ログの確認

【原則2】ネットワークの場所に関係なく、すべての通信を保護する
■実装要件
- すべての通信をTLS 1.3で暗号化
- VPN非依存のゼロトラストネットワークアクセス（ZTNA）実装
- 地理的位置による制御の無効化
■検証方法
- 通信暗号化の技術実証
- ZTNA機能のライブデモ
- 地理的制御無効化の設定確認

【原則3】企業リソースへのアクセスは、セッション単位で付与する
■実装要件
- すべてのアクセスをセッション単位で認証・認可
- セッション継続時間15分上限
- 作業完了時の自動セッション終了
■検証方法
- セッション管理のデモンストレーション
- タイムアウト動作の実証
- 自動終了機能の確認

【原則4】リソースへのアクセスは、動的ポリシーにより決定する
■実装要件
- 以下要素による動的スコアリング実装：
  - ユーザー信頼度（0-100点）
  - デバイス健全性（0-100点）
  - アクセス環境リスク（0-100点）
  - 時間帯係数（0.5-2.0倍）
  - リソース機密度（1-5レベル）
- 総合スコア60点未満の自動アクセス拒否
- スコア計算過程の可視化
■検証方法
- スコア計算ロジックのデモ
- 閾値動作の実証テスト
- 管理画面での確認

【原則5】すべての資産の整合性とセキュリティ動作を監視し、測定する
■実装要件
- 15分間隔での全デバイス自動監視
- 監視項目：OSパッチ、ウイルス定義、不正ソフト、設定変更、異常通信
- 異常検出時の即座自動隔離
- 修復完了までの復帰禁止
■検証方法
- 15分間隔監視の動作確認
- 異常検出シミュレーション
- 隔離・復旧プロセステスト

【原則6】すべてのリソース認証と認可は動的であり、アクセスが許可される前に厳密に実施する
■実装要件
- アクセス前の必須確認事項：
  - 多要素認証（生体認証+パスワード+デバイス証明書）
  - デバイスコンプライアンス確認
  - 条件付きアクセスポリシー評価
  - リアルタイム脅威インテリジェンス照合
- 確認完了前のデータアクセス完全禁止
- 確認処理3秒以内完了
■検証方法
- 認証フロー全体のテスト
- 処理時間の実測
- 確認前アクセス拒否の実証

【原則7】企業は、資産、ネットワーク、通信の現在の状態について可能な限り多くの情報を収集し、セキュリティ態勢の改善に利用する
■実装要件
- 24時間365日の情報収集：
  - 全アクセスログ（成功・失敗問わず）
  - デバイス状態変更履歴
  - ネットワーク通信パターン
  - アプリケーション使用状況
  - セキュリティアラート
- データの90日間保持
- 異常パターン検出AI機能
■検証方法
- ログ収集範囲の確認
- 90日間保持の実証
- AI検出機能のデモ

2.1.2 アーキテクチャ要件
以下の3つのコンポーネントを明確に分離して実装すること：

【Policy Engine（PE）】
■実装要件
- すべてのアクセス要求の最終判定
- 複数データソースからの情報統合
- リアルタイム脅威インテリジェンス連携
- 判定理由の完全ログ化

【Policy Administrator（PA）】
■実装要件
- PE判定に基づく通信パス制御
- セッション確立・終了の自動化
- 動的なポリシー更新反映
- 設定変更の即座適用

【Policy Enforcement Point（PEP）】
■実装要件
- 実際のアクセス制御実行
- すべての通信の監視・記録
- 異常検出時の即座遮断
- パフォーマンス影響の最小化
```
