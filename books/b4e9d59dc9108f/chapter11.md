## この章で学べること
- 技術点80点、価格点20点の科学的根拠に基づく配点設定
- 必須要件で足切りし、加点要件で差別化を図る評価手法
- デモンストレーションによる実技評価の具体的基準
- 過去実績の客観的評価方法とリスク判定
- そのまま使える配点表テンプレートと評価シート

## なぜこの章が重要なのか
価格だけで業者を選んだ結果、45万人分の個人情報が漏洩したX県の事例を忘れてはならない。安かろう悪かろうの提案を排除し、真にセキュアな提案を正確に見分けることが、あなたの使命である。評価基準の甘さが、明日の大事故につながる。

# 科学的な提案評価システム

## 11.1 必須要件と加点要件の設定

### 11.1.1 足切りライン：必須要件80項目
**要件**：以下の必須要件を1つでも満たさない提案は即座に失格とすること

子どもたちの個人情報保護に「妥協」はない。必須要件の例外は一切認めてはならない。1つの要件でも満たしていない提案者は、あなたの教育機関の情報セキュリティを理解していない証拠である。

```yaml
【A級必須要件】一つでも欠けたら即失格
NIST SP800-207準拠:
  - PE（Policy Engine）の具体的実装計画
  - PA（Policy Administrator）の設定詳細
  - PEP（Policy Enforcement Point）の配置設計
  - 継続的検証の実装方式
  - データ分類に基づくアクセス制御設計

Microsoft 365セキュリティ:
  - 条件付きアクセス15ポリシー以上設定
  - Microsoft Defender for Office 365 Plan 2機能活用
  - Microsoft Purview Information Protection設定
  - Microsoft Sentinel SIEM統合
  - 多要素認証100%強制設定

【B級必須要件】基本設定レベル
エンドポイントセキュリティ:
  - Microsoft Intune完全管理
  - Microsoft Defender for Endpoint Plan 2導入
  - デバイスコンプライアンスポリシー20項目以上
  - アプリケーション保護ポリシー設定
  - BYOD対策の明確化

データ保護:
  - 校務データの4段階分類定義
  - DLP（Data Loss Prevention）20ルール以上
  - 暗号化設定（保存時・転送時）
  - バックアップ・復旧手順
  - 監査ログの7年保管
```

#### 必須要件確認チェックリスト
提案書の以下の記載を確認し、1つでも「×」があれば即座に失格とせよ。

```yaml
技術要件確認:
□ NIST SP800-207の7原則すべてへの対応方法が具体的に記載されている
□ Microsoft 365 A3/A5の機能差を理解した上で適切な設定が提案されている
□ 125項目チェックリストのうち必須80項目すべてに回答がある
□ 設定値が具体的な数値で記載されている（「適切に設定」等の曖昧表現は×）
□ 教育機関特有の要件（校務支援システム連携等）への対応策がある

実装要件確認:
□ 段階的移行スケジュールが180日以内で設定されている
□ 並行運用期間が60日以上90日以内で計画されている
□ 切り戻し手順が30分以内で完了する具体的な計画がある
□ データ移行の完全性確保方法が明記されている
□ 移行テストを本番前に3回実施する計画がある

運用要件確認:
□ SOC要件（24時間365日監視）への具体的な体制が示されている
□ SLA要件（稼働率99.5%以上）への保証内容が明記されている
□ インシデント対応時間（重大：30分、軽微：2時間）が保証されている
□ Microsoft Secure Scoreの目標値（850点以上）が明記されている
□ 月次セキュリティレポートの提供が約束されている
```

### 11.1.2 差別化要件：加点要件45項目
**要件**：必須要件をクリアした提案のみ、加点要件で優劣を評価すること

```yaml
【S級加点要件】（各10点、最大50点）
先進的セキュリティ機能:
  - Microsoft Sentinel SOARによる自動対応設定
  - Microsoft Defender for Cloud Appsの高度分析
  - Azure AD Identity Protectionの機械学習活用
  - Microsoft 365 E5 Complianceの活用提案
  - カスタムセキュリティポリシーの独自開発

【A級加点要件】（各5点、最大100点）
運用高度化:
  - Microsoft Secure Score自動改善提案機能
  - PowerBIによる独自ダッシュボード提供
  - Microsoft Graph APIを活用した業務効率化
  - 教育機関向けカスタマイズ機能の開発
  - 隣接自治体との連携機能

【B級加点要件】（各2点、最大40点）
付加価値:
  - 研修プログラムの充実（年4回以上）
  - 24時間日本語サポート体制
  - 災害時BCP対応の具体化
  - コスト削減提案の具体性
  - 導入後3年間の無償サポート
```

## 11.2 技術点評価基準

### 11.2.1 技術点配点：800点満点
**要件**：技術点は総合評価の80%（800点）とし、以下の配点で厳格に評価すること

価格の安さに惑わされてセキュリティを犠牲にしてはならない。技術点重視の配点こそが、真に安全なシステムを選ぶ唯一の方法である。

```yaml
技術点内訳（合計800点）:

1. NIST SP800-207準拠性（200点）
   - PE実装設計：50点
   - PA実装設計：50点
   - PEP配置設計：50点
   - 継続的検証：50点

2. Microsoft 365設定（200点）
   - 条件付きアクセス設定：60点
   - セキュリティ機能設定：60点
   - データ保護設定：40点
   - 監視・レポート設定：40点

3. エンドポイントセキュリティ（150点）
   - Intune設定：50点
   - Defender for Endpoint設定：50点
   - デバイス管理ポリシー：30点
   - アプリ保護ポリシー：20点

4. 移行・運用計画（150点）
   - 移行計画の具体性：50点
   - 切り戻し計画：30点
   - 運用体制：40点
   - トレーニング計画：30点

5. 実績・体制（100点）
   - 教育機関導入実績：40点
   - 技術者資格・体制：30点
   - サポート体制：30点
```

#### 11.2.2 技術点評価の具体的基準
各項目の点数は以下の基準で厳格に評価せよ。主観的判断は排除し、客観的事実のみで採点すること。

```yaml
NIST SP800-207準拠性評価基準:
PE（Policy Engine）実装（50点満点）:
  50点: 校務システム専用ポリシーエンジンの詳細設計あり
  40点: 一般的なポリシーエンジン設計あり
  30点: 基本的なポリシーエンジン設計あり
  20点: ポリシーエンジンの概念説明のみ
  0点: ポリシーエンジンへの言及なし

PA（Policy Administrator）実装（50点満点）:
  50点: 校務データに特化したポリシー管理設計あり
  40点: 詳細なポリシー管理設計あり
  30点: 基本的なポリシー管理設計あり
  20点: ポリシー管理の概念説明のみ
  0点: ポリシー管理への言及なし

PEP（Policy Enforcement Point）配置（50点満点）:
  50点: 校務ネットワーク全体をカバーする詳細配置設計
  40点: 主要ポイントをカバーする配置設計
  30点: 基本的な配置設計
  20点: 配置の概念説明のみ
  0点: PEP配置への言及なし

継続的検証（50点満点）:
  50点: リアルタイム検証と自動対応の詳細設計
  40点: リアルタイム検証の設計あり
  30点: 定期的検証の設計あり
  20点: 検証の概念説明のみ
  0点: 継続的検証への言及なし
```

### 11.2.3 技術評価の実施手順
**要件**：技術評価は以下の手順で実施し、評価の客観性を確保すること

```yaml
評価実施体制:
評価委員構成:
  - 委員長：教育長
  - 技術評価委員：外部専門家2名（必須）
  - 業務評価委員：情報システム部長
  - 教育委員：学校現場代表1名
  - 事務局：調達担当者2名

評価プロセス:
1. 書面評価（5日間）:
   - 各委員が独立して採点
   - 根拠資料の明確化
   - 疑問点のリストアップ

2. ヒアリング評価（1日）:
   - 提案者への質疑応答
   - 疑問点の確認
   - 追加資料の要求

3. 最終評価（1日）:
   - 委員間での評価すり合わせ
   - 最終点数の確定
   - 評価理由の文書化

評価の透明性確保:
  - 全評価プロセスの録音・記録
  - 評価基準の事前公開
  - 評価結果の詳細フィードバック
```

## 11.3 デモンストレーション評価

### 11.3.1 実技評価：100点満点
**要件**：提案書だけでは判断できない実装能力を実技で確認すること

口先だけの美しい提案書に騙されてはならない。実際にシステムを構築し、運用できる技術力があるかどうかは、デモンストレーションでしか確認できない。

```yaml
デモ評価項目（合計100点）:

1. システム構築デモ（40点）
   必須シナリオ:
   - 新規ユーザー追加から初回ログインまで（10点）
   - 条件付きアクセスポリシーの動作確認（10点）
   - Microsoft Defender for Office 365の検知デモ（10点）
   - データ漏洩防止（DLP）の動作確認（10点）

2. セキュリティ対応デモ（30点）
   必須シナリオ:
   - 不正アクセス検知と自動ブロック（15点）
   - マルウェア検知と隔離処理（15点）

3. 運用管理デモ（30点）
   必須シナリオ:
   - Microsoft Secure Scoreの改善提案（10点）
   - インシデント対応フローの実演（10点）
   - レポート作成と分析（10点）
```

#### 11.3.2 デモ実施要件
**要件**：デモは本番同等環境で実施し、準備時間の制限を設けること

```yaml
デモ環境要件:
技術環境:
  - 本番同等のMicrosoft 365テナント
  - 実際の校務データ（匿名化）を使用
  - ネットワーク環境も本番に近似
  - 外部接続も含む完全環境

実施条件:
  - 準備時間：最大2時間
  - 実演時間：60分厳守
  - 質疑応答：30分
  - 評価委員全員が立会い

評価基準:
  完璧（10点）: エラーなく完了、説明も的確
  良好（8点）: 軽微なエラーあり、説明は適切
  普通（6点）: エラーあり、説明に不備
  不良（4点）: 重大なエラー、説明不十分
  失格（0点）: 完了できない、説明不能

デモ失格条件:
  - 制限時間内に完了できない
  - システムが正常動作しない
  - セキュリティ設定が不適切
  - 質問に答えられない（3回以上）
```

### 11.3.3 緊急時対応シミュレーション
**要件**：実際のインシデントを想定した対応力を評価すること

```yaml
シミュレーション内容:
シナリオ1: 不正アクセス発生（20点）
  設定: 校務システムへの外部からの不正アクセス
  要求対応:
  - 5分以内の検知確認
  - 10分以内のアクセス遮断
  - 15分以内の影響範囲特定
  - 30分以内の報告書作成

シナリオ2: マルウェア感染（20点）
  設定: 教職員PCでのマルウェア検知
  要求対応:
  - 即座の感染PC隔離
  - 5分以内の感染範囲調査
  - 10分以内の駆除処理
  - 15分以内の安全性確認

評価ポイント:
  - 対応スピードの適切性
  - 判断の正確性
  - コミュニケーション能力
  - ドキュメント作成能力
  - 二次被害防止能力
```

## 11.4 過去実績の評価方法

### 11.4.1 実績評価基準：客観的数値判定
**要件**：実績は客観的事実のみで評価し、営業文句に惑わされないこと

「豊富な実績」という曖昧な表現に騙されてはならない。具体的な数値と検証可能な事実のみで実績を評価せよ。虚偽の実績を申告する業者も存在するため、必ず裏取りを行うこと。

```yaml
実績評価項目（200点満点）:

1. 教育機関導入実績（100点）
   A評価（100点）: 同規模教育機関5件以上、稼働3年以上
   B評価（70点）: 同規模教育機関3-4件、稼働2年以上
   C評価（40点）: 同規模教育機関1-2件、稼働1年以上
   D評価（0点）: 教育機関実績なし

2. Zero Trust実装実績（50点）
   A評価（50点）: NIST SP800-207準拠実装5件以上
   B評価（35点）: NIST SP800-207準拠実装3-4件
   C評価（20点）: NIST SP800-207準拠実装1-2件
   D評価（0点）: Zero Trust実装実績なし

3. Microsoft 365大規模展開実績（50点）
   A評価（50点）: 1,000ユーザー以上展開5件以上
   B評価（35点）: 1,000ユーザー以上展開3-4件
   C評価（20点）: 1,000ユーザー以上展開1-2件
   D評価（0点）: 大規模展開実績なし

実績確認必須項目:
□ 導入先の組織名（守秘義務契約で開示）
□ 導入時期と稼働期間
□ ユーザー数と構成
□ 導入した機能の詳細
□ 稼働率実績（SLA達成度）
□ インシデント発生状況
□ 顧客満足度評価
```

#### 11.4.2 実績検証の実施方法
**要件**：申告実績の裏取りを必ず実施し、虚偽申告を排除すること

```yaml
実績検証手順:
1. 一次検証（書面確認）:
   - 契約書の写し（組織名黒塗り可）
   - 稼働確認書（顧客印付き）
   - SLA達成実績書
   - 顧客満足度調査結果

2. 二次検証（顧客ヒアリング）:
   - 無作為抽出した3社への直接確認
   - 電話ヒアリング（30分）
   - 確認項目：
     * 実際の稼働状況
     * システムの安定性
     * サポート品質
     * 継続利用の意向

3. 虚偽発覚時の対応:
   - 即座の失格処分
   - 3年間の入札参加禁止
   - 他自治体への情報共有

検証で確認する項目:
技術面:
  - 提案した技術の実際の実装状況
  - システムの安定稼働実績
  - セキュリティインシデントの発生状況
  - 性能目標の達成状況

運用面:
  - サポート対応の迅速性と的確性
  - 定期メンテナンスの実施状況
  - トラブル対応の満足度
  - 継続的改善の提案状況
```

#### 11.5.2 価格点算出方法
**要件**：価格点は最低価格者を基準とした相対評価で算出すること

```yaml
価格点計算式:
価格点 = (最低提案価格 ÷ 評価対象提案価格) × 200点

例：
最低提案価格: 5,000万円 → 200点
評価提案価格: 6,000万円 → 5,000÷6,000×200 = 166.7点
評価提案価格: 7,000万円 → 5,000÷7,000×200 = 142.9点

価格内訳評価:

  - システム構築費
```

### 11.5.4 最終選定基準
**要件**：以下の基準で最終的な業者選定を行うこと

```yaml
選定基準:
1. 必須要件: すべてクリア（1つでも×は失格）
2. 技術点: 600点以上（75%以上）
3. 総合点: 最高点の業者を選定

同点時の判定基準:
1位: NIST SP800-207準拠性の点数が高い
2位: 教育機関実績が多い
3位: Microsoft認定資格保有者が多い

選定結果の公開:
- 選定理由の詳細公開
- 各提案者への詳細フィードバック
- 評価基準の妥当性検証
- 次回調達での改善点反映
```

**真に安全なシステムを選ぶため、妥協なき評価を実行せよ。**

安い提案に飛びつく前に、子どもたちの個人情報が危険にさらされるリスクを考えよ。この章の評価基準に従えば、必ず最適な業者を選定できる。あなたの厳格な評価が、地域全体の情報セキュリティを守る砦となる。
