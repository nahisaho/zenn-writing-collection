## この章で学べること

- **Microsoft Sentinel 要件設定**: クラウドネイティブSIEMによる24時間365日監視体制の構築方法
- **SOC 要件の記載技法**: セキュリティオペレーションセンター機能を契約で確実に実現する仕様書作成手法
- **インシデント対応要件**: 校務データ漏洩発生時の初動対応から収束まで、時間軸で定義する完全対応フロー
- **数値 SLA 定義**: 検知時間、対応時間、復旧時間を具体的数値で規定し、ベンダー責任を明確化する手法
- **Microsoft Secure Score 活用**: 継続的セキュリティ改善のPDCAサイクルを契約で義務化する要件設計

## なぜこの章が重要なのか

**セキュリティ対策を実装しても、監視体制がなければ攻撃を見逃す。** 2024年の教育機関サイバー攻撃では、初期侵入から発見まで平均287日を要し、その間に45万人分の個人情報が窃取された。しかし、適切な監視・対応要件を仕様書に組み込めば、攻撃を24時間以内に検知し、72時間以内に完全封じ込めできる。

この章では、実際に大規模攻撃を早期発見・封じ込めに成功した監視体制要件を公開する。あなたがこの章を読み終える頃には、どんな巧妙な攻撃も見逃さない監視体制を契約で確実に実現できる調達仕様書が完成している。

# 8.1 Microsoft Sentinel要件

## クラウドSIEMの絶対的優位性

**オンプレミスSIEMでは現代のサイバー攻撃に対応できない。** 従来型 SIEM の脅威検知能力は60％程度で、特にクラウドサービスを狙った攻撃を見逃す。Microsoft 365 環境を狙った攻撃を確実に検知するには、Microsoft Sentinel によるクラウドネイティブ監視が必須である。

### Microsoft Sentinel必須機能要件

```
Microsoft Sentinel要件 第14条（クラウドSIEM実装）

1. 基本構成要件
   1.1 Microsoft Sentinel Standard プラン以上
       - 1日あたりログ取り込み：最低1TB以上対応
       - データ保持期間：最低2年間
       - 高可用性：99.9%以上のSLA保証

   1.2 連携データソース（必須）
       - Microsoft 365 全サービスのログ
       - Microsoft Entra ID サインインログ・監査ログ
       - Microsoft Defender全製品のアラート
       - Windows Security イベント
       - 校務支援システムのログ（Syslog/CEF形式）

2. 検知ルール実装要件
   2.1 教育機関特化検知ルール（必須20種）
       - 成績データ大量ダウンロード検知
       - 深夜・休日の異常アクセス検知
       - 複数アカウントでの同期ログイン検知
       - 個人情報検索クエリ異常実行検知
       - 外部IPからの管理者権限使用検知

   2.2 Microsoft標準検知ルールの全有効化
       - Advanced Hunting クエリ200種以上
       - MITRE ATT&CK フレームワーク準拠検知
       - Machine Learning ベース異常検知

3. 自動対応（SOAR）要件
   3.1 即座実行アクション
       - 疑わしいアカウントの自動無効化
       - 異常IP アドレスの自動ブロック
       - 管理者への即時アラート送信
       - インシデントチケット自動作成

   3.2 段階的対応アクション
       - 15分以内：初期アラート発生
       - 30分以内：詳細分析レポート生成
       - 1時間以内：影響範囲特定完了
       - 2時間以内：封じ込めアクション実施
```

## 校務システム統合監視要件

**Microsoft 365 だけを監視しても意味がない。校務支援システムとの統合監視が攻撃全体像把握の鍵である。** システム間の不整合や連携部分での攻撃を見逃せば、気づいた時には全システムが侵害されている。

### システム統合監視仕様

```
統合監視要件 第15条（マルチシステム監視）

1. 校務支援システム監視
   1.1 ログ転送設定
       - Syslog RFC5424 準拠形式
       - CEF（Common Event Format）対応
       - TLS 1.3 暗号化転送必須
       - ログ欠損時のアラート機能

   1.2 監視対象イベント
       - 管理者権限でのログイン・ログアウト
       - 大量データエクスポート実行
       - データベース直接アクセス
       - 設定変更・権限変更操作
       - バックアップ取得・復元操作

2. 相関分析ルール
   2.1 システム横断攻撃検知
       - 校務システム侵害→Microsoft 365 侵入パターン
       - 同一IPからの複数システム攻撃
       - 時系列相関による持続的攻撃検知
       - 権限昇格攻撃の段階的検知

   2.2 業務パターン学習
       - 正常業務フローのベースライン構築
       - 季節要因（入試・卒業等）の自動考慮
       - 勤務時間外アクセスの文脈判断
       - 職員の行動パターン逸脱検知

3. 可視化・レポート要件
   3.1 統合ダッシュボード
       - 全システムセキュリティ状況を1画面表示
       - リアルタイム脅威レベル表示
       - インシデント対応状況の進捗表示
       - 月次・四半期セキュリティサマリー

   3.2 役職別レポート自動配信
       - CIO向け：戦略的セキュリティ状況
       - 情報システム担当者向け：技術詳細
       - 管理職向け：業務影響とリスク評価
       - 監査部門向け：コンプライアンス状況
```

# 8.2 SOC要件の記載方法

## 教育機関専用SOC体制

**汎用 SOC サービスでは教育機関の特殊性に対応できない。** 校務データの機微性、学校行事スケジュール、長期休暇期間などの教育機関特有の要因を理解しない SOC 担当者では、適切な判断ができない。教育機関専門のSOC体制を契約で義務化せよ。

### SOC人材・体制要件

```
SOC 体制要件 第16条（専門SOC構築）

1. 人材要件
   1.1 教育機関専門チーム編成
       - 教育業界セキュリティ経験3年以上
       - 校務支援システム知識保有者
       - 文科省ガイドライン理解者
       - Microsoft 365 Education 認定資格保有者

   1.2 24時間365日体制
       - レベル1アナリスト：2名以上常駐
       - レベル2アナリスト：オンコール30分以内
       - レベル3エキスパート：オンコール1時間以内
       - インシデントマネージャー：オンコール15分以内

2. 対応時間SLA
   2.1 検知・初期対応
       - Critical：15分以内に初期対応開始
       - High：30分以内に初期対応開始
       - Medium：2時間以内に初期対応開始
       - Low：8時間以内に初期対応開始

   2.2 エスカレーション基準
       - 個人情報漏洩の可能性：即座にCritical扱い
       - 校務システム停止：即座にHigh扱い
       - 権限昇格攻撃検知：30分でHigh扱い
       - 異常アクセス継続：1時間でMedium扱い

3. 通知・連絡体制
   3.1 即時通知対象者
       - 教育長・副教育長
       - 情報システム担当部長
       - 学校事務担当課長
       - 外部委託先責任者

   3.2 通知方法の多重化
       - メール・SMS・電話での同時通知
       - 専用アプリでのプッシュ通知
       - 緊急時庁内放送システム連携
       - 首長部局危機管理部門への自動連絡
```

## SOC 業務範囲の明確化

**SOC の業務範囲が曖昧だと責任逃れが発生する。** 検知・分析・対応・報告の各段階で、SOC担当者と発注者側の役割分担を明確に契約で規定しなければならない。

### 業務分掌・責任範囲

```
SOC 業務要件 第17条（責任範囲明確化）

1. SOC側責任範囲
   1.1 監視・検知業務
       - 24時間365日リアルタイム監視
       - 異常検知アラートの1次分析
       - 脅威レベル判定と優先度設定
       - 初期封じ込め対応の実施

   1.2 分析・調査業務
       - フォレンジック調査の実施
       - 攻撃手法・影響範囲の特定
       - 類似攻撃の予兆検知
       - 対策提案書の作成・提出

   1.3 報告業務
       - インシデント発生30分以内の速報
       - 24時間以内の詳細報告書提出
       - 週次セキュリティサマリー作成
       - 月次改善提案書の提出

2. 発注者側責任範囲
   2.1 意思決定・承認業務
       - 重大インシデント時の対外発表判断
       - 法執行機関への通報判断
       - システム停止・復旧の最終判断
       - 保護者・議会への説明実施

   2.2 内部調整業務
       - 関係部署への情報共有
       - 校長会・教育委員会への報告
       - 報道対応・広報業務
       - 被害届提出等の法的手続き

3. 連携業務（共同実施）
   3.1 インシデント対応
       - 初動対応（SOC主体・発注者承認）
       - 封じ込め作業（SOC実施・発注者調整）
       - 復旧作業（SOC支援・発注者主体）
       - 事後検証（共同実施）

   3.2 改善活動
       - 脆弱性対策（SOC提案・発注者判断）
       - セキュリティポリシー見直し（共同検討）
       - 職員教育計画（SOC助言・発注者実施）
       - システム更改時のセキュリティ要件（共同策定）
```

# 8.3 インシデント対応要件

## 教育機関特化インシデント対応フロー

**教育機関のインシデント対応は企業と全く異なる。** 保護者・地域住民への説明責任、議会対応、マスコミ対応、法執行機関との連携など、教育機関特有の複雑な利害関係者への対応が必要である。これらを時系列で明確に契約化せよ。

### インシデント対応タイムライン

```
インシデント対応要件 第18条（対応フロー・時系列）

1. 初動対応（0-2時間）
   1.1 検知・確認フェーズ（0-30分）
       - SOC：異常検知・アラート発報
       - SOC：1次分析・脅威レベル判定
       - 発注者：緊急連絡網による情報共有
       - 発注者：インシデント対策本部設置準備

   1.2 初期封じ込めフェーズ（30分-2時間）
       - SOC：攻撃源IP・アカウントの特定・遮断
       - SOC：影響システム・データの特定
       - 発注者：関係部署への初期情報共有
       - 発注者：外部専門家への支援要請検討

2. 本格対応（2-24時間）
   2.1 詳細分析フェーズ（2-8時間）
       - SOC：フォレンジック調査開始
       - SOC：攻撃手法・侵入経路の特定
       - 発注者：被害範囲の業務的影響評価
       - 発注者：法執行機関通報要否の検討

   2.2 封じ込め・復旧フェーズ（8-24時間）
       - SOC：完全封じ込め作業実施
       - SOC：システム復旧支援・検証
       - 発注者：業務継続計画（BCP）発動
       - 発注者：保護者・関係者への初期連絡

3. 事後対応（24時間-30日）
   3.1 調査・報告フェーズ（1-7日）
       - SOC：詳細調査報告書作成
       - SOC：再発防止策の提案
       - 発注者：関係機関への正式報告
       - 発注者：保護者説明会・個別対応

   3.2 改善・再発防止フェーズ（7-30日）
       - SOC：セキュリティ強化策実装
       - SOC：監視体制見直し・強化
       - 発注者：内部処分・責任追及
       - 発注者：制度・運用ルール見直し

4. 長期フォロー（30日-1年）
   4.1 継続監視・支援
       - SOC：強化監視体制による再発防止
       - 発注者：被害者へのフォローアップ
       - 共同：再発防止策の効果検証
       - 共同：類似攻撃への備え強化
```

## 法的対応・危機管理要件

**サイバー攻撃は刑事事件である。適切な法的対応を怠れば、二次被害が拡大する。** 証拠保全、法執行機関連携、報告義務履行を時系列で義務化し、法的リスクを最小化せよ。

### 法的手続き・報告義務

```
法的対応要件 第19条（法執行機関連携）

1. 刑事手続き対応
   1.1 証拠保全義務
       - インシデント発生4時間以内：ログ・証跡の完全保全
       - フォレンジックイメージ取得：24時間以内完了
       - 証拠チェーンの維持：改ざん防止措置実施
       - 法執行機関提出用データ整備

   1.2 被害届・告訴準備
       - 警察署サイバー犯罪対策課への相談：24時間以内
       - 被害届作成支援：SOC・発注者共同実施
       - 告訴状作成支援：必要に応じて弁護士連携
       - 捜査協力体制の構築

2. 行政報告義務
   2.1 文部科学省への報告
       - 重大事案報告：24時間以内（第一報）
       - 詳細報告書：7日以内提出
       - 対応状況報告：月次提出
       - 再発防止策報告：事案解決後30日以内

   2.2 個人情報保護委員会への報告
       - 個人情報漏洩報告：72時間以内（GDPR準拠）
       - 影響評価書：14日以内提出
       - 対策実施報告：随時更新
       - 類似事案予防策報告

3. 議会・住民対応
   3.1 議会報告・答弁
       - 緊急議会報告：重大事案発生1週間以内
       - 詳細説明資料作成：SOC技術支援
       - 議員質問への回答準備
       - 百条委員会等への対応支援

   3.2 住民・保護者対応
       - 緊急保護者説明会：事案公表3日以内
       - 個別相談窓口設置：被害発生時即座
       - FAQ作成・公表：よくある質問への回答整備
       - 長期フォローアップ体制構築

4. 損害賠償・保険対応
   4.1 損害調査・算定
       - 直接被害額の算定：会計監査法人連携
       - 間接被害・風評被害の評価
       - 対応費用・復旧費用の集計
       - 精神的被害・慰謝料の検討

   4.2 保険金請求・支払い
       - サイバー保険への事故報告：24時間以内
       - 保険会社との調整・交渉支援
       - 保険金支払い条件の確認・調整
       - 免責事項への対応・交渉
```

# 8.4 SLA 定義の方法

## 数値で規定する性能保証

**曖昧な SLA は責任逃れの温床である。** 検知時間、対応時間、復旧時間、可用性を具体的数値で規定し、達成できない場合のペナルティまで明記しなければならない。教育機関の業務特性を考慮した実現可能かつ厳格な SLA を設定せよ。

### 監視・対応SLA定義

```
監視対応 SLA 第20条（数値性能保証）

1. システム監視 SLA
   1.1 監視可用性
       - 監視システム稼働率：99.9%以上/月
       - 監視データ欠損率：0.1%以下/月
       - 監視遅延時間：平均30秒以内
       - 監視範囲カバレッジ：100%（除計画メンテナンス）

   1.2 検知性能
       - Critical 攻撃検知：平均15分以内
       - High脅威検知：平均30分以内
       - 異常行動検知：平均1時間以内
       - 誤検知率：5%以下（月次測定）

2. インシデント対応 SLA
   2.1 対応開始時間
       - Critical：15分以内（達成率95%以上）
       - High：30分以内（達成率90%以上）
       - Medium：2時間以内（達成率85%以上）
       - Low：8時間以内（達成率80%以上）

   2.2 解決時間
       - Critical：4時間以内（封じ込め完了）
       - High：8時間以内（影響範囲特定・対策実施）
       - Medium：24時間以内（調査・対策完了）
       - Low：72時間以内（恒久対策実施）

3. 復旧・継続性 SLA
   3.1 システム復旧時間
       - 校務システム：4時間以内（業務時間内）
       - Microsoft 365：2時間以内
       - ネットワーク基盤：1時間以内
       - 監視システム自体：30分以内

   3.2 データ整合性保証
       - データ損失：0件（完全バックアップ前提）
       - データ復旧精度：100%
       - 業務継続性：代替手段含め80%以上維持
       - 証跡保全：改ざん・欠損なし100%

4. SLA 未達成時ペナルティ
   4.1 段階的減額措置
       - 軽微違反（月1-2回）：月額費用1%減額
       - 中程度違反（月3-5回）：月額費用3%減額
       - 重大違反（月6回以上）：月額費用5%減額
       - 継続的違反：契約解除権行使可能

   4.2 追加ペナルティ
       - 重大インシデント対応遅延：50万円/回
       - データ損失発生：損害額の全額賠償
       - 法令違反招致：弁護士費用・制裁金負担
       - 信頼失墜招致：風評被害賠償
```

## 教育機関特化 SLA 設計

**教育機関の業務特性を無視したSLAは絵に描いた餅である。** 入試期間、卒業式、新年度準備等の重要時期、夏季休暇等の長期休業期間、災害時等の緊急時における異なる SLA 基準を設定し、真に実効性のある性能保証を実現せよ。

### 業務特性別 SLA 基準

```
教育機関特化 SLA 第21条（業務連動性能保証）

1. 重要時期強化 SLA（入試・卒業・新年度）
   1.1 対象期間
       - 入試実施期間（2-3月）
       - 卒業式・修了式期間（3月）
       - 新年度準備期間（3-4月）
       - 成績処理集中期間（7月、12月、3月）

   1.2 強化性能基準
       - システム可用性：99.99%以上
       - Critical対応：5分以内開始
       - システム復旧：30分以内完了
       - 24時間専任担当者配置

2. 長期休業期間調整 SLA（夏季・冬季・春季休業）
```

## まとめ：24時間365日監視体制の完全実装

この章で定義した監視・対応要件を仕様書に組み込めば、どんな巧妙な攻撃も見逃さない鉄壁の監視体制を構築できる。重要なポイント：

1. **Microsoft Sentinel による統合監視**で全システムの脅威を一元把握
2. **教育機関専門SOC体制**で業界特性に応じた的確な判断・対応実現
3. **時系列インシデント対応フロー**で初動から法的対応まで完全網羅
4. **数値SLA・ペナルティ規定**でベンダー責任を明確化し確実な性能保証
5. **継続改善PDCA制度**で長期的なセキュリティ成熟度向上を実現

**次の第9章では、これらの高度なセキュリティ体制を運用する人材要件を解説する。** 適切な人材配置・役割分担・教育体制により、技術的対策を確実に機能させる組織体制の構築方法を完成させる。
