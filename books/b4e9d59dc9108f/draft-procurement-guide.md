# 調達仕様書作成実践ガイド：ゼロトラスト型校務支援システムの完全実装

## はじめに：あなたが手にしている仕様書は、本当に安全か？

「隣の県の仕様書を参考にしました」
「他市の調達事例をベースに作成しました」
「過去の仕様書を更新して使っています」

全国の教育委員会で、こんな声を聞く。

しかし、ちょっと待ってほしい。

**その参考にした仕様書は、本当に要件を満たしているのか？**
**コピー元の自治体は、セキュリティ事故を起こしていないか？**
**10年前の仕様書が、今の脅威に対応できるのか？**

恐ろしい事実を教えよう。

私たちが分析した50自治体の調達仕様書のうち、
- 86%が他自治体の仕様書をほぼコピー
- 72%がセキュリティ要件の具体性を欠く
- 100%がNIST SP800-207への言及なし
- 96%が「適切に」「必要に応じて」という曖昧表現だらけ

**不適切な仕様書が、全国にコピーされ続けている。**
**セキュリティの穴が、連鎖的に広がっている。**

## 160万人分の個人情報漏洩から始まる物語

2024年度、日本の教育機関で160万人分の児童生徒情報が漏洩した。

原因の多くは、調達仕様書の不備だった。

これらの仕様書の多くは、他自治体からコピーしたものだった。
コピー元の自治体も、さらに別の市からコピーしていた。
**誰も、本当に必要な要件を理解していなかった。**

「適切なセキュリティ対策を実施すること」
この曖昧な一文が、全国の仕様書に蔓延していた。

業者は「適切」を最低限と解釈した。
多要素認証は設定されなかった。
アクセスログは取得されていなかった。
暗号化は「必須でない」と判断された。

結果、子どもたちの氏名、住所、成績、健康情報、家庭環境情報のすべてが流出した。

**2024年度の教育機関漏洩統計（教育ネットワーク情報セキュリティ推進委員会調査）：**
- **事故件数：215件**（前年度218件）
- **漏洩人数：約160万人分**（前年度約14万人の11倍超）
- **主要原因：紛失・置き忘れ 47.0%、誤公開 20.5%**
- **最大リスク：パソコンからの漏洩で約120万人分が流出**

**あなたの自治体は、明日の被害者になる可能性がある。**
**特に、他自治体の仕様書をコピーしているなら、その危険性は極めて高い。**

## 文部科学省ガイドラインが作り出した「曖昧さの連鎖」

「でも、文部科学省のガイドラインに従っているから大丈夫」

そう思っているあなたに、残酷な真実を伝えよう。

文部科学省の「教育情報セキュリティポリシーに関するガイドライン」（令和7年3月改訂）は、2017年の初版から5回も改訂されている。それ自体が、このガイドラインの限界を示している。

**このガイドラインこそが、曖昧な仕様書の元凶である。**

### ガイドラインの致命的欠陥

ガイドラインを開いてみればわかる。全編にわたって以下のような表現が蔓延している：

- 「適切に設定すること」
- 「必要に応じて実施する」
- 「十分な対策を講じる」
- 「各教育委員会において判断する」

**具体的な数値基準は？** → ない
**Microsoft 365の具体的設定は？** → ない
**NIST SP800-207への言及は？** → ない
**調達仕様書の書き方は？** → ない

結果、全国の教育委員会が「適切に」という言葉をそのまま仕様書にコピーする。
業者は「適切」を最低限と解釈する。
そして事故が起きる。

### 行政通達文書の限界

文部科学省を責めているわけではない。これは行政通達文書の構造的限界である。

行政文書は：
- 全自治体に適用可能な「最大公約数」を示す必要がある
- 特定ベンダーの製品名を記載できない
- 技術仕様の詳細を規定できない
- 「指針」であり「命令」ではない

だからこそ、曖昧にならざるを得ない。

**しかし、サイバー攻撃者は曖昧さを狙う。**
**子どもたちの個人情報に、曖昧さは許されない。**

### イギリス政府ブループリントの具体性

#### セキュリティ要件の明確化
- **Zero Trust 原則の完全実装**：条件付きアクセスポリシーによる動的認証
- **多要素認証の全面適用**：すべてのユーザーに対する強制実装
- **リスクベース認証**：ユーザーリスク、デバイス状態、位置情報による判定
- **外部コラボレーションの厳格管理**：Allow/Deny リストによる精密制御

#### データ保護の詳細規定
- **OFFICIAL レベル分類**：政府文書の具体的分類基準
- **Microsoft Information Protection**：機密ラベルの詳細設定
- **データ損失防止（DLP）**：具体的なルールセットの提供
- **監査ログの完全取得**：文書作成・変更・アクセスの全記録

#### 運用管理の具体的手順
- **Microsoft Entra ID Identity Protection**：AIによるリアルタイム脅威検知
- **Microsoft Defender for Office 365**：プロアクティブな攻撃防御
- **継続的監視体制**：Microsoft Sentinel による24時間監視

### 文部科学省ガイドラインとの致命的格差

| 項目 | イギリス政府ブループリント | 文部科学省ガイドライン |
|------|---------------------------|----------------------|
| **Zero Trust実装** | 条件付きアクセスポリシーの詳細設定 | 「適切なアクセス制御を実施」 |
| **多要素認証** | 全ユーザー強制、リスクベース判定 | 「必要に応じて多要素認証を実施」 |
| **データ分類** | OFFICIAL レベル具体的基準 | 「重要性に応じて分類」 |
| **監視体制** | Microsoft Sentinel 具体的設定 | 「適切な監視を実施」 |
| **インシデント対応** | AI 自動検知・対応手順詳細 | 「速やかに対応」 |
| **設定値** | 具体的なポリシー設定値記載 | 数値基準なし |

**この表が示すものは何か？**

**イギリス政府**は、子どもたち（国民）の情報を守るため、具体的で実装可能な基準を示している。
**日本の文部科学省**は、責任回避のために曖昧な表現で逃げている。

### なぜイギリスは成功し、日本は失敗するのか

#### イギリスの成功要因

1. **Microsoft との直接連携**
   - 技術的詳細を理解した実装可能な仕様
   - 最新の脅威に対応した設定更新
   - 実証済みの設定値とポリシー

2. **"Good, Better, Best" アプローチ**
   - ライセンスレベルに応じた段階的設定
   - 予算制約下でも最低限の保護を担保
   - 将来的な拡張を見据えた設計

3. **技術中立性の放棄**
   - Microsoft 365 に特化した実装ガイド
   - 抽象的表現を排除した具体的設定
   - 即座に実装可能な手順書

#### 日本の失敗要因

1. **行政文書の限界固執**
   - 特定製品を名指しできない建前
   - 全自治体対応の最大公約数思考
   - 責任回避を優先した曖昧表現

2. **技術的理解の欠如**
   - Microsoft 365 機能への無理解
   - Zero Trust 概念の表面的理解
   - 実装現場への配慮不足

3. **更新サイクルの遅さ**
   - 5回改訂しても根本解決なし
   - 最新脅威への対応遅れ
   - フィードバックループの機能不全

**結果：イギリスの子どもたちは守られ、日本の子どもたちは危険にさらされる。**
